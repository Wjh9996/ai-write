## 4. 进阶篇

### 4.1 SSE 与实时通信

**要掌握**：
- SSE 帧格式：`id: / data: / event: / \n\n`
- `Last-Event-ID` 是浏览器自动带的，服务端必须按它补发
- SseEmitter 的超时/完成/错误回调
- 断线 ≠ 任务停止（任务在服务端线程池里跑，与连接生命周期解耦）

**在本项目**：`02` §4 三件套。

**动手**：
1. 打开创作台开始生成，**中途刷新页面**，观察重连后正文是否继续增长（应该继续，因为事件已落库）。
2. 打开两个标签页同时看同一个 job，验证多连接广播。
3. 把 `awaitFirstConnection` 的 2500ms 改成 0，看开头事件会不会丢。

### 4.2 并发控制的三层防线

**要掌握**：应用层校验 → 数据库约束 → 异常兜底，缺一层都不完整。

**在本项目**：`02` §5。

**动手**：用两个终端同时 curl 创建同章任务，看谁成功谁被拒，看拒绝信息来自哪一层。

```bash
curl -X POST http://127.0.0.1:8080/api/chapters/1/generation-jobs \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"idempotencyKey":"a"}' &
curl -X POST http://127.0.0.1:8080/api/chapters/1/generation-jobs \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"idempotencyKey":"b"}' &
```

### 4.3 乐观锁 vs 悲观锁

**要掌握**：
- 乐观锁适合"冲突少、响应要快"的编辑场景（本项目）
- 悲观锁（`SELECT ... FOR UPDATE`）适合"冲突频繁"的库存/秒杀场景
- 版本号递增要**精确控制触发条件**（这就是 Chapter 手写 version 而不是用 `@Version` 的原因）

**动手**：打开两个浏览器标签同时编辑同一章，都点保存，观察第二个收到 409。

### 4.4 事务边界与"部分成功"

**要掌握**：审核入库要写四类数据（摘要/角色状态/时间线/伏笔）。没有事务会出现"摘要写进去了但时间线没写"的脏数据。

**动手**：把 `approve()` 的 `@Transactional` 去掉，在 `plantForeshadowing` 里手动抛异常，然后查库看摘要是否已经写入（应该写入了 —— 这就证明了事务的必要性）。

### 4.5 AI 工程：上下文是有损压缩

**要掌握**：
- 长篇上下文不能无限堆，必须压缩：正文 → 摘要 → 设定变更
- 只有**人工确认过**的信息才能进上下文（否则错误会累积放大）
- `reveal_chapter` 防止"未来信息泄露"到当前章节

**在本项目**：`ReviewService.approve` 是唯一写回入口；`SettingEntity.revealChapter`。

**动手**：
1. 给一个角色设 `revealChapter = 10`，然后在 `renderPrompt` 里加过滤逻辑（当前章 < 10 时不把它放进上下文）。
2. 写测试证明：第 5 章的提示词里不含该角色，第 10 章含。

### 4.6 成本模型

**要掌握**：
```
单章成本 ≈ 输入 tokens × 单价 + 输出 tokens × 单价
输入 ≈ 上下文包（6k tokens）× 5 段 + 系统提示
输出 ≈ 2500 字 × 1.5 ≈ 3.75k tokens
```
本项目的 `usage_records` 每次模型调用都记账，`UsageService` 按场景聚合。

**动手**：接真实模型后跑 10 章，用实际账单校准 `input-price-per-k` / `output-price-per-k`（文档 §11 明确要求实测校准，现在配置里是估算值）。

### 4.7 长篇一致性：自检能做什么、不能做什么

**要掌握**：
- 规则校验能查：角色越界、字数越界、章纲越界（确定性，100% 可靠）
- 模型自检能查：语气漂移、重复表述、情节逻辑（概率性，**不能宣称零幻觉**）
- 正确姿态：模型只提"带正文引文的问题"，最终由人判断

**在本项目**：`ReviewService.checkConsistency`（规则） + 预留模型自检接口。

## 5. 专家篇

### 5.1 MySQL 生成列替代 partial index

**要掌握**：
```sql
col TYPE AS (expr) [VIRTUAL|STORED]
-- VIRTUAL：不占存储，读取时计算（本项目选择）
-- STORED：落盘，可建二级索引
```
MySQL 唯一索引允许多个 NULL，这是"部分唯一"能成立的关键。

**延伸思考**：
- 如果要"每章最多 2 个活动任务"怎么办？（提示：生成列做不了，需要应用层计数 + 锁）
- STORED vs VIRTUAL 的取舍？

### 5.2 事件溯源式的 SSE 持久化

**要掌握**：把事件流当成事实来源（source of truth）：
- 事件落库 + 单调递增 seq → 天然支持补读、重放、审计
- 状态（章节内容）是事件的投影
- 任务结束时必须等异步落库写完（`awaitWrites`），否则补读会缺尾部

**延伸**：这套模式再往前一步就是 CQRS / Event Sourcing。本项目只用在生成流上，是很好的入门案例。

### 5.3 流式削峰

**要掌握**：
- 模型吐字是突发的，前端渲染是连续的 → 需要削峰（`stream-interval-ms`）
- 切块要**保持标点完整**（`TextKit.splitChunks` 在标点处断句，不在任意字符处断）
- 落库要异步，否则 I/O 成为瓶颈（实测 90s → 10s）

**延伸**：如果并发 100 个用户在生成，单线程事件落库会不会成为瓶颈？怎么分片？

### 5.4 幂等设计

**要掌握**：
- 幂等键要由**客户端生成**（本项目 `key-{chapterId}-{timestamp}`）
- 服务端用唯一索引 + 命中返回，而不是抛错
- 幂等 ≠ 锁：幂等解决"重复提交"，锁解决"并发执行"

### 5.5 可观测性

**本项目已做**：`requestId` 贯穿前后端、`usage_records` 记账、`audit_logs` 留痕。

**还差**（可作为扩展任务）：
- 结构化日志（JSON 格式 + traceId）
- 生成任务的耗时埋点（P50/P95）
- 模型调用失败率与重试次数

## 8. 故障排查手册

| 现象 | 排查顺序 |
|---|---|
| 后端启动失败：`Unsupported character encoding` | JDBC URL 的 `characterEncoding` 必须是 `UTF-8` |
| 后端启动失败：`bean 'requestContextFilter'` | 自定义过滤器不能占用内置 bean 名 |
| 满屏"找不到符号" | 先修掉其它编译错误（重复类/缺包），Lombok 才会生效 |
| SSE 收不到开头事件 | 检查 `runAsync` 的 `awaitFirstConnection`；或看是不是任务已跑完才连 |
| 生成特别慢（几十秒） | 检查事件落库是否同步；检查 `stream-interval-ms` |
| 生成字数超出 2700 | mock 网关的 `buildText` 是否按目标字数截断 |
| 前端报"服务端返回了非 JSON 响应" | 检查是不是把二进制流接口当 JSON 调了（导出） |
| 前端登录后接口 403 | token 没存（真实模式下 `login` 要 `setToken(profile.token)`） |
| 前端请求 502（本地） | 沙箱/代理把 127.0.0.1 也代理了，用 `curl --noproxy '*'` 或 `NO_PROXY=*` |
| `mvn` 拉不到依赖 | parent 是不是 SNAPSHOT；换正式版或加镜像 |
| 改了 Java 代码没生效 | devtools 会重启，但需先 `mvn compile`；或确认端口没被旧进程占着 |

## 附：三条最值得记住的设计原则

1. **规则要落到数据库，不能只写在文档里** —— 应用层校验会被绕过，唯一索引不会。
2. **上下文必须是有损压缩，而且只进人工确认过的信息** —— 这是长篇 AI 创作能不能成立的根本。
3. **不可靠的东西（模型）只负责提议，可靠的东西（规则 + 人）负责决定** —— 自检只提带引文的问题，写回必须经过人。
