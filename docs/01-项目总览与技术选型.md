## 1. 这个项目到底解决什么问题

### 1.1 真实的痛点

用 AI 写长篇小说，直接把"给我写第 30 章"丢给模型，会撞上三堵墙：

| 墙 | 表现 | 后果 |
|---|---|---|
| **上下文墙** | 一部 100 万字的书，单次模型上下文装不下 | 写到第 30 章，模型已经忘了第 3 章埋的伏笔 |
| **一致性墙** | 模型不知道"这个角色此刻不知道这件事" | 写出角色提前知道结局的荒谬段落 |
| **成本墙** | 每次都把全书喂给模型 | 一章几块钱，一本书几千块，个人扛不住 |

### 1.2 这个项目的解法

不追求"模型一次写完整本书"，而是**把长篇拆成可控制的工程流水线**：

```
总纲（人工写，几千字）
   ↓  AI 拆
卷纲事件（人工列 5—10 条）
   ↓  AI 拆
章纲（每章 3—7 个 beat，必须人工确认）  ← 规则①：未确认不许生成正文
   ↓  五段流式生成
一章 2500 字（逐句长出，可随时停止）
   ↓  自检 + 摘要 + 设定变更草稿
人工点「通过并入库」→ 摘要/角色状态/时间线/伏笔 同一事务写回
   ↓
下一章的上下文 = 总纲 + 已确认摘要 + 已确认设定（而不是全书正文）
```

**核心思想**：让"上下文"随章节推进**有损压缩**（正文 → 摘要 → 设定变更），而不是无限堆积。这样第 30 章的上下文成本和第 3 章一样，而且只包含**人工确认过**的信息。

### 1.3 六条不可妥协规则（整套代码的灵魂）

代码里所有看似啰嗦的校验，都是这六条规则的落地。读代码时先记住这张表：

| # | 规则 | 代码位置 |
|---|---|---|
| ① | 未确认的章纲不得生成正文 | `ChapterGenerationService.start()` 校验 `outline.status == CONFIRMED` |
| ② | AI 不得直接修改已确认内容 | 生成只写 `chapter.contentMd` 的待审草稿，不碰设定 |
| ③ | 摘要/设定变化需人工确认才回写 | `ReviewService.approve()` 是唯一写回入口 |
| ④ | 正文唯一权威版本 | `chapters.content_md` 是唯一真相，版本历史在 `chapter_versions` |
| ⑤ | AI 不得覆盖人工编辑 | `content_version` 乐观锁，冲突返回 409 |
| ⑥⑦ | 一章只允许一个活动生成任务 | 应用层 `findActiveByChapter` + 数据库 `uk_active_chapter` 双保险 |
| ⑧ | 所有写入按 user_id + novel_id 校验 | `Ownership.requireNovel()` 被每个 Controller 调用 |

## 4. 关键决策记录（ADR）

### ADR-1：MySQL 而不是 PostgreSQL

**设计文档原本写的是 PostgreSQL**（用 `JSONB` + `partial unique index`）。最终选 MySQL，理由：

| 维度 | PostgreSQL | MySQL 8 | 判定 |
|---|---|---|---|
| JSON | `JSONB` + GIN 索引、`@>` 包含查询、单 key 更新 | `JSON`，无 GIN，JSON 内索引要靠生成列 | **不影响**：本项目所有 JSON 都是整存整取，不做 JSON 内部检索 |
| 部分唯一索引 | 原生支持 | 不支持 | **唯一硬差距**，已用生成列解决（见下） |
| UUID 类型 | 原生 | `CHAR(36)` | 影响小，前端 jobId 是字符串 |
| MVCC / DDL 事务 | 更彻底 | InnoDB MVCC，DDL 隐式提交 | MVP 单用户感知不到 |
| 中文全文检索 | 需插件 | 内置 ngram parser | MySQL 略优，首版没用上 |
| 向量检索 | pgvector 成熟 | 无原生向量类型 | **未来若做"相似章节召回"，这是唯一值得换 PG 的理由** |
| 本机环境 | 需另装 | 3306 已在跑 | 决定性 |

**生成列方案（本项目最值得讲的技术点）**：

规则⑦要求"一章同一时刻只能有一个 QUEUED/RUNNING 的任务"。

```sql
-- PostgreSQL 写法（部分索引，MySQL 没有）
CREATE UNIQUE INDEX uk_active ON generation_jobs(chapter_id)
  WHERE status IN ('QUEUED','RUNNING');

-- MySQL 等价实现：虚拟生成列 + 唯一索引（MySQL 唯一索引允许多个 NULL）
active_key BIGINT AS (CASE WHEN status IN ('QUEUED','RUNNING','STOP_REQUESTED')
                           THEN chapter_id ELSE NULL END) VIRTUAL,
UNIQUE KEY uk_active_chapter (active_key)
```

**实测证据**（本机 MySQL 8）：
```
INSERT ... ('t1', 999, 'RUNNING')  → 成功
INSERT ... ('t2', 999, 'RUNNING')  → ERROR 1062 Duplicate entry '999' for key 'uk_active_chapter'
INSERT ... ('t3', 999, 'COMPLETED')→ 成功（已完成任务允许并存）
```

> 面试讲法：不要说"PG 有这个功能 MySQL 没有所以我不如 PG"，要说"PG 用语法糖解决，MySQL 用生成列解决，效果等价且由数据库强制，不靠应用层自觉"。

### ADR-2：JPA 而不是 MyBatis

设计文档写「JPA 或 MyBatis 二选一，首版推荐 MyBatis」。实际选 JPA：

- MyBatis-Plus 3.5.x 的自动配置（`MybatisPlusAutoConfiguration`）尚未适配 Spring Boot 4 / Spring Framework 7，强行引入大概率启动失败；
- Hibernate 由 Spring Boot 官方 starter 保证兼容；
- 本项目查询模式简单（按 `novel_id`、`volume_id`、`chapter_no` 查），JPA 派生查询足够；
- `@JdbcTypeCode(SqlTypes.JSON)` 让 JSON 列映射变透明，这是 MyBatis 需要手写 TypeHandler 的地方。

### ADR-3：SSE 而不是 WebSocket / 轮询

| 方案 | 单向/双向 | 断线重连 | 实现成本 | 结论 |
|---|---|---|---|---|
| 轮询 | 单向 | 无 | 低 | 每秒几十次 delta，轮询会打爆接口 |
| WebSocket | 双向 | 需自己实现 | 高 | 本项目只需要服务端→客户端单向推，用不上双向 |
| **SSE** | 单向 | **浏览器原生自动重连 + Last-Event-ID** | 中 | ✅ |

关键：SSE 的断线补读是协议自带的。本项目把事件落库（`generation_events.event_seq` 单调递增），客户端重连时带 `Last-Event-ID`，服务端补发该序号之后的全部事件。

### ADR-4：五段流式生成而不是一次吐完

一章 2500 字一次性生成的问题：
1. 用户盯着白屏 15 秒，像卡死；
2. 中途想停掉，只能等它写完；
3. 模型输出越长越容易跑偏，且单次输出上限可能被截断。

拆成五段（500/550/450/450/550）后：
- 边写边看，随时停（停止只取消未开始的后续段，已写的保留）；
- 每段可以单独重试/继续；
- 前端按段显示进度条。

### ADR-5：ModelGateway 可插拔

没有 API Key 也要能跑通整条闭环 → 抽象 `ModelGateway` 接口：

```java
public interface ModelGateway {
    void stream(ModelRequest request, Consumer<ModelChunk> onChunk);
    List<ChapterOutline> generateOutlines(String prompt, int total, int skip);
    String complete(String system, String user);
}
```

- `MockModelGateway`：本地语料流式吐字（与前端 mock 同源），`novel.ai.provider=mock`；
- `OpenAiCompatibleGateway`：任意 OpenAI 兼容接口（DeepSeek/通义/豆包/Kimi），`provider=openai` + `AI_API_KEY`。

切换只改配置，**业务代码一行不动**。

### ADR-6：Spring Boot 4 的破坏性变更清单（踩过的）

| 变化 | 旧 | 新 |
|---|---|---|
| WebMVC starter 名 | `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| Jackson 包 | `com.fasterxml.jackson.*` | `tools.jackson.core.*` |
| 测试注解包 | `...test.autoconfigure.web.servlet.AutoConfigureMockMvc` | `...boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` |
| `andExpect(matcher, message)` 重载 | 支持 | 移除（只接受 matcher） |
| `URI.parse(String)` | 不存在 | 只有 `URI.create(String)` |
| 内置 bean 名 `requestContextFilter` | 可占用 | 已被内置，自定义同名会启动失败 |

## 5. 数据模型总览

19 张表，分五组：

| 组 | 表 | 关键字段 / 设计点 |
|---|---|---|
| **账号** | `users` | `password_hash`(BCrypt)、`monthly_quota_chars`、`used_chars` |
| **作品与大纲** | `novels`、`volumes`、`chapter_outlines` | `volumes.events_json`(JSON 数组)、`chapter_outlines.beats_json`(3—7 条)、`status` 区分 DRAFT/CONFIRMED |
| **章节** | `chapters`、`chapter_versions` | `chapters.content_md` 唯一权威；`content_version` 乐观锁；`chapter_status` 状态机 |
| **设定库** | `setting_entities`、`world_settings`、`timeline_events`、`foreshadowings`、`summaries`、`style_profiles` | `source`(AI/MANUAL) + `approval_status`(只有 CONFIRMED 进上下文)；`reveal_chapter` 防止提前泄露 |
| **生成与质量** | `generation_jobs`、`generation_segments`、`generation_events`、`context_snapshots`、`audit_reports`、`setting_change_drafts`、`usage_records`、`audit_logs` | `generation_jobs.active_key` 生成列；`generation_events.event_seq` 递增；`usage_records` 记账 |

### 章节状态机

```
OUTLINED ──start──> GENERATING ──完成──> REVIEW_PENDING ──approve──> APPROVED
                        │                      │
                        └──停止──> REVIEW_PENDING  └──reject──> GENERATING
```

> 注意：没有 `APPROVED → 重新生成` 的自动路径。已入库的章节要重写属于 P1 功能（本地重写），不在首版范围。

## 8. 五分钟跑起来

```bash
# 1. 数据库（MySQL 8，本机 root/123456）
mysql -u root -p123456 < back/ai-write/src/main/resources/schema.sql
```
