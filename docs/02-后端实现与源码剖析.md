## 1. 包结构与分层职责

```
com.wjh.aiwrite
├── common/     ApiResult, BizException, GlobalExceptionHandler, RequestContext(Filter)
├── config/     SecurityConfig, TokenAuthenticationFilter, CurrentUser, AppConfig, AiProperties
├── support/    Ownership（权限）, TextKit（字数/切句/TXT 解析）
├── auth/       model/User, repository, service/TokenService, controller/AuthController
├── novel/      model/Novel, repository, dto, service/NovelService, controller
├── outline/    model/Volume+ChapterOutline, repository, dto, service/OutlineService, controller
├── setting/    model/(6 张表), repository, dto, service/SettingService, controller
├── chapter/    model/Chapter+ChapterVersion, repository, dto, service, controller
├── generation/ model/(job/segment/event), repository, dto, service/(流水线+SSE Hub+ModelGateway), controller
├── review/     model/(audit/change draft), repository, dto, service/ReviewService, controller
├── usage/      model/UsageRecord, repository, dto, service, controller
└── export/     service/ExportService, controller/ExportController
```

| 层 | 该做什么 | **不该**做什么 |
|---|---|---|
| `controller` | 参数校验、权限校验、调 service、包 `ApiResult` | 写业务规则、直接碰 repository |
| `service` | 业务规则、状态机、事务边界、编排 | 出现 `HttpServletRequest`、拼 JSON 响应 |
| `repository` | 数据访问（派生查询 / JPQL） | 写业务判断 |
| `model` | 实体与字段约束 | 写业务逻辑 |
| `dto` | 视图模型（全部 `record`，与前端模型字段一一对应） | 出现 JPA 注解 |

**为什么 DTO 全用 record**：Java 21 的 record 天然不可变、自带 equals/toString，做"视图模型"最省代码。本项目 15 个 DTO 全是 record，平均每个 20 行以内。

## 2. 一次请求的完整生命周期

```
HTTP 请求
  ↓ ① RequestContextFilter（@Order -100）：分配 requestId，写回 X-Request-Id
  ↓ ② TokenAuthenticationFilter（@Order -90）：解析 token → SecurityContext
  ↓ ③ DispatcherServlet → Controller：参数校验（@Valid）
  ↓ ④ Controller：ownership.requireNovel(novelId)  ← 规则⑧
  ↓ ⑤ Service：业务规则 + 事务
  ↓ ⑥ Repository：JPA
  ↓ 返回：ApiResult { code, message, data, requestId }
  ↓ 异常：GlobalExceptionHandler 统一转成 ApiResult
```

### 2.1 统一响应

```java
public record ApiResult<T>(int code, String message, T data, String requestId) {
    public static <T> ApiResult<T> ok(T data) {
        return new ApiResult<>(0, "ok", data, RequestContext.requestId());
    }
    public static <T> ApiResult<T> fail(int code, String message) { ... }
}
```

`requestId` 由 `RequestContext`（ThreadLocal）+ 过滤器注入，前后端一串号排查问题。

### 2.2 鉴权的双通道

SSE 的 `EventSource` 和 `<a download>` 都**不能自定义请求头**，所以 token 要走 query：

```java
private String resolveToken(HttpServletRequest request) {
    String header = request.getHeader(HttpHeaders.AUTHORIZATION);
    if (header != null && header.regionMatches(true, 0, "Bearer ", 0, 7)) {
        return header.substring(7).trim();      // 普通 REST
    }
    return request.getParameter("token");        // SSE / 文件下载
}
```

> 这个设计让"导出 docx"这件事不需要单独做一套鉴权：前端把 token 拼在下载 URL 上即可。

### 2.3 权限校验集中在一处

```java
public Novel requireNovel(Long novelId) {
    Novel novel = novelRepository.findById(novelId)
            .orElseThrow(() -> BizException.notFound("作品不存在"));
    if (!novel.getUserId().equals(userId())) {
        throw BizException.forbidden("无权访问该作品");   // 403
    }
    return novel;
}
```

每个 Controller 的第一行都是它。测试 `AuthApiTest.cannotAccessOthersNovel` 专门验证两个不同账号都访问不了别人的作品。

### 2.4 异常码即 HTTP 状态码

```java
public class BizException extends RuntimeException {
    private final int code;
    public static BizException conflict(String m) { return new BizException(HttpStatus.CONFLICT, m); } // 409
    public static BizException forbidden(String m) { ... }  // 403
    public static BizException notFound(String m) { ... }   // 404
}
```

前端 `http.ts` 里判断 `code !== 0` 就抛错，不用再解析 HTTP 状态。

## 3. 核心：单章生成流水线

文件：`generation/service/ChapterGenerationService.java`（约 300 行，全项目最核心）

### 3.1 启动前的四道校验（`start()`）

```java
// ① 幂等：相同 key 直接返回已有任务，重复点击「生成本章」不会产生第二份正文
if (idempotencyKey != null && !idempotencyKey.isBlank()) {
    Optional<GenerationJob> dup = jobRepository.findByIdempotencyKey(idempotencyKey);
    if (dup.isPresent()) return dup.get();
}

// ② 规则①：章纲必须已确认
if (outline != null && !"CONFIRMED".equals(outline.getStatus())) {
    throw new IllegalStateException("本章章纲尚未确认，不能生成");
}

// ③ 规则⑦：一章一个活动任务
if (!jobRepository.findActiveByChapter(chapterId).isEmpty()) {
    throw new IllegalStateException("本章已有进行中的生成任务");
}

// ④ 规则②：前一章未审核，不能写下一章
if (chapter.getChapterNo() > 1) { ...前一章必须是 APPROVED... }
```

### 3.2 主循环（`run()`）

```java
List<Integer> targets = segmentTargets();     // [500, 550, 450, 450, 550]
int from = resumePoint(job);                  // 从最后一个完整段的下一号继续
StringBuilder whole = new StringBuilder(baseContent(job, chapter));

for (int i = from; i <= targets.size(); i++) {
    if (Boolean.TRUE.equals(stopFlags.get(jobId))) break;   // 停止点：段与段之间

    emit(job, "segment.started", Map.of("segment", ...));

    modelGateway.stream(new ModelRequest(systemPrompt, prompt, target, model),
        chunk -> {
            buf.append(chunk.delta());
            emit(job, "text.delta", Map.of("segmentNo", segNo, "text", chunk.delta()));
        });

    // 分段落库（停止后可从这里恢复）
    seg.setContent(text); seg.setStatus("COMPLETED"); segmentRepository.save(seg);
    emit(job, "segment.completed", Map.of("segmentNo", segNo, "written", countWords(text)));
    recordUsage(jobId, "分段生成", estimateTokens(prompt), estimateTokens(text));
}
```

三个关键设计：

**(1) 停止语义**：`stopFlags` 只在段之间检查。正在写的那一段会写完，未开始的段直接跳过。已生成内容保留并写入章节 —— 对应文档 §4.3「停止只取消未开始的后续段」。

**(2) 恢复语义**：`resumePoint()` 取最后一个 `COMPLETED` 段的下一号，`baseContent()` 把已完成段拼回来作为前缀。断点续写不需要重跑全部。

**(3) 生成完不自动入库**：只把章节置为 `REVIEW_PENDING`，摘要/设定必须等人工点「通过」。这是规则③。

### 3.3 提示词组包（`renderPrompt` / `systemPrompt`）

```
system = 文风卡（从 style_profiles 读） + 禁止项
user   = 【本章章纲】beats
        【相关角色卡】出场角色名
        【上一段结尾】上一章/上一段末尾 200 字
        任务：写第 N/5 段，X 字左右，承接上文，只推进本段 beat，结尾留钩子
```

注意：**上下文里只有"已确认"的设定和摘要**，不塞全书正文。这就是 §1.2 说的"有损压缩"。

## 4. SSE 三件套

### 4.1 SseHub：连接管理

```java
private final Map<String, List<SseEmitter>> emitters = new ConcurrentHashMap<>();

public SseEmitter create(String jobId) {
    SseEmitter emitter = new SseEmitter(30 * 60 * 1000L);   // 30 分钟
    emitters.computeIfAbsent(jobId, k -> new CopyOnWriteArrayList<>()).add(emitter);
    emitter.onCompletion(() -> remove(jobId, emitter));
    emitter.onTimeout(() -> remove(jobId, emitter));
    ...
}
```

一个 job 可以有多个连接（多标签页同时看），断了只摘掉自己那一个，**不影响任务继续跑**。

### 4.2 emit：同步推送 + 异步落库

```java
private void emit(GenerationJob job, String type, Map<String, Object> payload) {
    long seq = seqCounters.computeIfAbsent(job.getId(), k -> new AtomicLong(0)).incrementAndGet();

    GenerationEvent e = new GenerationEvent();
    e.setJobId(job.getId()); e.setEventSeq(seq); e.setEventType(type);
    e.setPayloadJson(json);

    // 落库丢给专用单线程，绝不能阻塞生成循环
    pendingWrites.incrementAndGet();
    eventWriter.execute(() -> {
        try { eventRepository.save(e); }
        finally { pendingWrites.decrementAndGet(); }
    });

    // 实时推送是同步的
    sseHub.send(job.getId(), Map.of("seq", seq, "type", type, "payload", payload), seq);
}
```

**为什么落库必须异步**：一次生成会产生 300+ 条 `text.delta`。实测逐条同步 `save` 会把 10 秒的生成拖到 **90 秒**（H2/MySQL 每次 save 都要开事务 + flush）。改成异步后回到 10 秒。任务收尾时调 `awaitWrites()`（最长等 5 秒）确保尾部事件写完。

### 4.3 断线补读

```java
@GetMapping(value = "/generation-jobs/{jobId}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter events(@PathVariable String jobId,
                         @RequestHeader(value = "Last-Event-ID", required = false) String lastEventId) {
    SseEmitter emitter = sseHub.create(jobId);
    long from = parseSeq(lastEventId);
    if (from > 0) {
        eventRepository.findByJobIdAndEventSeqGreaterThanOrderByEventSeq(jobId, from)
                .forEach(e -> sseHub.send(jobId, toFrame(e), e.getEventSeq()));
    }
    return emitter;
}
```

`event_seq` 单调递增是这套机制的前提 —— 测试 `GenerationPipelineTest.fullPipeline` 里专门断言了这一点。

### 4.4 一个容易忽略的竞态

POST 创建任务后如果**立即**开跑，客户端还没连上 SSE，开头几个事件就发完了。解法：

```java
public void runAsync(String jobId) {
    executor.execute(() -> {
        sseHub.awaitFirstConnection(jobId, 2500);   // 最多等 2.5 秒让客户端连上
        run(jobId);
    });
}
```

后端不能依赖前端一定连上来，所以是"等一会再开跑"而不是"等到了才跑"。

## 5. 并发控制：三层防线

规则⑦「一章只有一个活动任务」由三层保证：

| 层 | 实现 | 作用 |
|---|---|---|
| 应用层 | `findActiveByChapter()` 查询 | 快速失败，给出友好报错 |
| 数据库层 | `uk_active_chapter`（生成列 + 唯一索引） | **即使绕过应用层也拦得住**（MySQL 实测 1062） |
| 异常兜底 | `GlobalExceptionHandler` 捕获 `DataIntegrityViolationException` | 把数据库错误翻译成"本章已有进行中的生成任务" |

第三层的代码：

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ApiResult<Void> handleDataConflict(DataIntegrityViolationException e) {
    String root = e.getMostSpecificCause().getMessage();
    if (root != null && root.contains("uk_active_chapter")) {
        return ApiResult.fail(409, "本章已有进行中的生成任务，不能重复创建");
    }
    ...
}
```

幂等则是另一条线：`idempotency_key` 唯一索引 + `findByIdempotencyKey` 命中直接返回。前端每次点「生成本章」带 `key-{chapterId}-{timestamp}`，重放同一个 key 不会产生第二份正文。

## 6. 乐观锁与审核事务

### 6.1 乐观锁（规则⑤）

注意本项目有**两种**版本控制，别混：

| 实体 | 方式 | 用途 |
|---|---|---|
| `Novel`、`ChapterOutline` | JPA `@Version` | 防止并发改同一条记录 |
| `Chapter` | **手写** `content_version` 字段 | 正文编辑的乐观锁，可控性更强（JPA 的 @Version 会在任何 save 时递增，包括只改状态） |

```java
if (expected != c.getContentVersion()) {
    throw BizException.conflict("正文已被其他操作更新，请刷新后再保存");   // 409
}
// 先留版本历史，再更新正文
ChapterVersion v = new ChapterVersion();
v.setChapterId(id); v.setVersionNo(c.getContentVersion());
v.setContentMd(c.getContentMd()); v.setEditorType("HUMAN");
versionRepository.save(v);

c.setContentMd(req.contentMd());
c.setContentVersion(c.getContentVersion() + 1);
```

**为什么手写**：`chapter` 表同时存正文和状态（`chapter_status`）。用 `@Version` 会导致"改个状态"也让正文版本号 +1，那 AI 保存时就会莫名其妙冲突。手写能精确控制"只有正文内容变了才递增版本号"。

### 6.2 审核事务（规则③）

```java
@Transactional
public void approve(Long chapterId, ApproveRequest req) {
    // 校验：摘要非空、changes 非空
    for (ChangeDto ch : req.changes()) {
        if (!ch.accepted()) continue;                 // 人工逐条勾选
        switch (ch.kind()) {
            case "CHARACTER_UPDATE" -> updateCharacter(...);       // 角色状态
            case "TIMELINE"        -> settingService.appendTimeline(...);   // 时间线
            case "FORESHADOWING"   -> settingService.plantForeshadowing(...); // 伏笔
            case "NEW_ENTITY"      -> createEntity(...);           // 新设定（带 reveal_chapter）
        }
    }
    c.setChapterStatus("APPROVED");
    c.setAuditStatus("PASSED");
    c.setContentVersion(c.getContentVersion() + 1);
}
```

一个 `@Transactional` 包住四类写操作，**要么全成功要么全回滚**。测试 `ReviewServiceTest` 覆盖了三条分支：全部接受、全部不接受（什么都不写）、新增设定。

### 6.3 自检只提"带引文的问题"

```java
// 规则 1：正文出现设定库里没有的名字
if (!known.contains(candidate)) {
    issues.add(new IssueDto("i-" + candidate, "越界", "MID",
        candidate,                                          // quote：正文引文
        "正文中出现了设定库里没有的名字「" + candidate + "」",
        "确认是笔名/地名，或把它登记进设定库"));
}
// 规则 2：字数区间
// 规则 3：章纲越界（没有确认 beat 时判 HIGH）
```

对应文档 §4.4 的要求：**只提出带正文引文的问题，不宣称零幻觉**。模型自检（接真模型后）会补充软性问题，规则校验负责硬问题。

## 7. 踩坑清单（每个都有根因）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 满屏"找不到符号"，全是 getter/setter | 工程里还有别的编译错误（重复类、找不到包）时，**javac 会跳过注解处理轮次**，Lombok 静默失效 | 先修掉非 Lombok 错误，Lombok 自动恢复。排查顺序很重要 |
| 2 | `程序包 com.fasterxml.jackson.databind 不存在` | Spring Boot 4 用 **Jackson 3**（`tools.jackson.core`） | 需要显式声明 jackson-databind 依赖时注意版本；业务代码里直接用 `ObjectMapper`（Jackson 2 亦可，但要知道 Spring 自己用的是 3） |
| 3 | `spring-boot-starter-validation` 拉不到 | parent 是 `4.0.10-SNAPSHOT`，公共镜像无对应快照 | 切到正式版 `4.0.8` |
| 4 | `Unsupported character encoding 'utf8mb4'` | Connector/J 9.x 只认 `UTF-8`，不认 `utf8mb4` | JDBC URL 改 `characterEncoding=UTF-8` |
| 5 | `URI.parse()` 编译失败 | JDK 只有 `URI.create()` | 替换 |
| 6 | `The bean 'requestContextFilter' could not be registered`（启动失败） | 与 Spring Boot 内置同名 bean 冲突 | 组件改名 `@Component("requestIdFilter")` |
| 7 | SSE 收集耗时 90 秒 | 300+ 条事件逐条同步落库 | 异步单线程落库 + 收尾 `awaitWrites()` |
| 8 | 客户端收不到 `job.started` | POST 后立即开跑，SSE 还没连上 | `runAsync` 前 `awaitFirstConnection(2500)` |
| 9 | 生成字数 2831，超出 2700 上限 | mock 语料整段追加，没有按目标字数截断 | `buildText` 按句截断到本段目标字数 |
| 10 | `andExpect(matcher, message)` 编译失败 | Spring Framework 7 移除了带 message 的重载 | 只传 matcher，注释说明意图 |

## 8. 数据库设计深挖

### 8.1 JSON 列的映射

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "beats_json")
private List<String> beats = new ArrayList<>();

@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "card_json")
private Map<String, String> card = new LinkedHashMap<>();
```

Hibernate 7 直接把 `List<String>` / `Map<String,String>` 映射到 MySQL `JSON` 列，读写透明。

**MySQL JSON vs PostgreSQL JSONB 的实际差异**（本项目结论）：

| 能力 | JSONB | MySQL JSON | 本项目是否需要 |
|---|---|---|---|
| GIN 索引 / `@>` 包含查询 | ✅ | ❌ | 不需要（不做 JSON 内部检索） |
| 单 key 更新 | ✅ | 需整体覆盖 | 不需要（卡片是整存整取） |
| 表达式索引（生成列） | ✅ | ✅ | 需要时可用 |

### 8.2 索引设计

| 表 | 索引 | 目的 |
|---|---|---|
| `generation_jobs` | `uk_active_chapter(active_key)` 唯一 | 规则⑦ |
| `generation_jobs` | `uk_idempotency(idempotency_key)` 唯一 | 幂等 |
| `generation_events` | `uk_events_job_seq(job_id, event_seq)` 唯一 | 补读不能重复 |
| `chapters` | `uk_chapters_novel_no(novel_id, chapter_no)` 唯一 | 章号不重复 |
| `chapters` | `idx_chapters_status(novel_id, chapter_status)` | 列表按状态过滤 |
| `chapter_outlines` | `uk_outlines_volume_no(volume_id, chapter_no)` 唯一 | 章纲顺序 |

### 8.3 字符集

全部 `utf8mb4`。建库语句里显式指定：

```sql
CREATE DATABASE ai_write DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
```

> 注意：`utf8mb4_general_ci` 对中文够用且排序快；若要更精确的中文排序可用 `utf8mb4_zh_0900_as_cs`（MySQL 8 支持），但本项目不做中文排序检索。

### 8.4 长文本字段

正文用 `LONGTEXT`（MySQL），JPA 侧用 `@Lob`。一章 2500 字远远没到上限，但导出全书时会一次性读 18 章正文进内存 —— 这是已知的待优化点（长篇应改流式导出）。
